Three kinds of proof

Read time: 6 minutes. One win: you can say exactly what TLA+, Z3 and CBMC prove, what they do not, and which one to reach for.

Rule of the house: a proof is always a proof about a model. The map is not the territory. TLA+ checks a state machine you wrote, Z3 checks arithmetic you wrote, CBMC checks C within bounds you chose. None of them proves the physical board works — that is what the serial logs are for.

0. Why three tools, not one

Different questions need different kinds of answer. You caught the distinction yourself when you asked how we prove a button works a billion times: testing gives you samples; proof gives you a bound over a model.

We use three tools because they answer three different questions:

  • TLA+: can the state machine ever reach a bad state?
  • Z3: is this arithmetic statement true for every possible input?
  • CBMC: can this C function violate an assertion within these bounds?

1. TLA+ — check the state machine, not the code

You write a tiny model in session.tla: variables, an initial state, and the possible next steps. TLC (the model checker) explores every reachable state and checks your named invariants. Our session model has five variables and a deliberately tiny set of session IDs (0–3), so the whole graph is 13 states and finishes in one second.

What it proved: LINK UP never occurs without ECDH keys, session ID 0 never coexists with LINK UP, keys never exist without a session, and a pending ECDH derivation always has a session.

Boundary: we modelled five variables. The real firmware has radio state, lwIP callbacks, watchdog timing and a dozen other variables. TLC found no bug in the model. If the model is wrong, the proof is worthless — that is the whole craft.

Think of it like: proving a chess puzzle has no checkmate in one. You enumerated every legal move. You did not prove your opponent plays well.

2. Z3 — an oracle for "is this always true?"

Z3 is a satisfiability solver. You give it a statement and it either finds a counterexample (sat) or proves none exists (unsat). Our script proves seven facts, including:

  • 85 glyphs × 3 symbols = 255, which fits in a uint8_t position field;
  • a serial number cannot be simultaneously "newer" and "older" than another;
  • wraparound from 0xFFFFFFFF to 0 is correctly recognised as newer;
  • an ID inside the 8-slot ratchet window is never treated as newer.

Boundary: Z3 proved arithmetic about uint32 serial numbers and byte limits. It cannot tell you whether the KDF is collision-resistant or whether the radio works. And a proof is only as honest as the statement — my first script encoded a wrong definition of "older" and Z3 correctly reported a counterexample. The tool caught my mistake, not the code's.

Think of it like: a calculator that never makes arithmetic mistakes, but only answers the exact question you typed.

3. CBMC — bounded checking of the C itself

CBMC takes real C code, replaces inputs with nondeterministic values, unwinds loops to a bound, and asks a SAT solver whether any input can violate an assertion. Our staged harness asks: can proto_frame_decode ever accept a frame whose payload pointer lands outside the buffer? Can encode/decode ever fail to round-trip a payload of 0–64 bytes?

Status here: harness written, not run — the Windows installer failed (MSI 1603). Do not let anyone tell you it passed.

Boundary: "bounded" means exactly that. It checks lengths up to the bound you chose. A bug requiring a longer input is not covered. It also does not prove the compiler generated correct machine code — that is what CompCert is for.

Think of it like: checking every possible key on a keyring of a fixed size. A key you did not put on the ring was not tested.

4. Which one do I reach for?

QuestionTool
"Can my protocol ever get into a bad state?"TLA+
"Is this arithmetic true for every uint32?"Z3
"Can this C function crash or read out of bounds?"CBMC
"Does the radio actually link up?"Serial log. No tool replaces hardware.

5. Test yourself

TLC found no error in 13 states. What did it prove?
A) The firmware has no bugs   B) The model has no reachable bad state   C) The radio works
B — The model has no reachable bad state. Wrong model, worthless proof. Hardware logs stay separate.
Z3 returned 'unsat' for your statement. What happened?
A) No counterexample exists   B) The code is correct   C) The tool timed out
A — No counterexample exists for that statement. It says nothing about code you did not encode.
CBMC checked payloads up to 64 bytes. What about 65?
A) Proven safe too   B) Rejected by the compiler   C) Outside the bound, not checked
C — Outside the bound, not checked. Bounded means bounded; say so in the claim.
